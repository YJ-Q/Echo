# Margin V1 Phase 2.5 Multi-Workstream Continuity Validation Design

Date: 2026-08-24
Status: approved direction, pending written-spec review
Baseline: `77a910ae6aff7536400c2b8cd240774b63899b9c`

## 1. Goal

Phase 2.5 turns the accepted Phase 2B Workbench into the first version that the
owner can use during real, frequently interrupted work.

The product loop is:

```text
inspect active Workstreams
-> choose one Workstream
-> restore its verified working context
-> accept or edit a next action
-> work through one governed Run
-> checkpoint before switching
-> restore another Workstream without re-explaining it
```

The phase validates one product claim: Margin reduces the cost and error rate
of switching among several long-running Workstreams while preserving user
control.

It does not attempt to complete the Personal Agent OS vision in one release.
It establishes the trusted continuity loop on which Daily Brief, Personal
Model, mobile capture, scheduling, and safe execution can later depend.

## 2. Confirmed user behavior and product problem

The owner frequently switches among projects, job seeking, learning, and other
work. A single-Workstream daily-focus product would not match this behavior.

The first usable version must therefore support:

- several visible active Workstreams;
- one foreground Workstream at a time, without hiding the others;
- a fast, evidence-backed resume experience after every switch;
- strict context isolation between Workstreams;
- preservation of decisions, state, next actions, and confirmed memory across
  browser, server, and runtime Session boundaries.

Morning and evening routines are supporting views. They are not mandatory
rituals and are not the primary product loop.

## 3. Behavioral constitution

### 3.1 Loyalty

Margin is loyal to the user's reviewed and revisable long-term direction while
protecting the user's final authority over their own choices.

Margin is not loyal to every immediate command, and it is not loyal to an
Agent-inferred idea of the user's welfare.

### 3.2 Evidence order

When identifying a conflict, Margin considers evidence in this order:

1. explicit safety boundaries and the user-confirmed personal constitution;
2. confirmed long-term goals and current priorities;
3. prior decisions with observed outcomes;
4. unconfirmed behavioral patterns and forecasts;
5. the current instruction.

This is not a rule that long-term interests always defeat short-term interests.
Intervention strength also depends on reversibility, consequence, evidence
quality, and urgency.

### 3.3 Intervention levels

Margin uses the least forceful adequate intervention:

1. assist normally;
2. identify missing information;
3. explain a conflict and offer an alternative;
4. temporarily hold a high-risk or constitution-conflicting action for
   explicit confirmation;
5. after informed override, carry out the allowed action and record the
   decision without moral judgment.

Independent platform, legal, and system-safety restrictions are not user
overridable. Margin must not present those restrictions as Personal Model
judgments.

### 3.4 Override learning

An informed override records the relevant goal, Margin's evidence summary, the
user's choice, and the later observable result. A repeated conflict prompts a
proposal to review the constitution or priority. It does not automatically
increase resistance or label the user as irrational.

### 3.5 Personal Model authority

Margin may infer candidate patterns. An inferred pattern cannot constrain a
decision until the user confirms it. Unconfirmed patterns may support a
question or weak suggestion only.

Phase 2.5 implements these principles in suggestion evidence, memory review,
and conflict handling. It does not build a complete constitution engine or a
global Personal Model.

## 4. Chosen product approach

Three approaches were considered:

- a morning/evening planning loop, which is visible but risks producing generic
  reports before enough evidence exists;
- a universal inbox, which lowers capture friction but risks becoming an
  information warehouse without an action loop;
- a Multi-Workstream continuity loop, which directly addresses frequent
  switching and reuses the accepted Core.

Phase 2.5 chooses the Multi-Workstream continuity loop. Morning Portfolio and
Evening Review may summarize the same authoritative state and Events, but they
must not introduce separate daily-plan state.

## 5. Frozen architecture principles

- Persistent Core remains the only Source of Truth.
- Every Surface continues to use only `execute(command)`, `query(query)`, and
  `events(query)` for durable application behavior.
- The Web client owns view selection, open panels, temporary form content, and
  loading markers only.
- Conversation is a Surface and runtime experience, not a business database.
- Pi is a replaceable Runtime Adapter. A Pi Session identifier remains only a
  `runtimeReference`.
- Event records facts. Activity remains an Event-derived projection.
- A generated Resume Brief or suggestion is not evidence that state changed.
  Only successful Contract results and Events are evidence.
- No raw Chain of Thought, model internals, prompts, or Pi objects are exposed.
- No second SQLite database, browser shadow state, or direct repository access
  is introduced.

The Gateway method surface remains exactly `execute`, `query`, and `events`.
Phase 2.5 may add backward-compatible command, query, DTO, and Event types under
an additive Contract version; it must not create a fourth transport method.

Phase 2.5 advances `CONTRACT_VERSION` from `1.0` to `1.1`. Existing Phase 2B
commands, queries, routes, envelopes, and DTO fields remain compatible.

The additive Contract types are:

- commands: `workstream.switch`, `memory.confirm`, `memory.correct`,
  `memory.archive`, and `memory.restore`;
- queries: `resume_brief.get`, `memory.list`, and `memory.search`;
- events: `memory.proposed`, `memory.confirmed`, `memory.superseded`,
  `memory.archived`, and `memory.restored`.

`workstream.switch` is host-controlled. It accepts source Workstream and Run
coordinates, the source Run expected version, and a target Workstream id. It
halts and checkpoints the source when required, then returns the refreshed
source state and a target Resume Brief. It never starts the target Run; target
start or resume remains a separate explicit user command.

`resume_brief.get` is read-only. Its DTO contains bounded fact sections,
source entity ids and versions, unresolved NeedsOwner references, and one
primary recommendation plus at most two alternatives. It contains no prompt,
raw conversation, model reasoning, or runtime object.

## 6. Portfolio and focus model

The Workbench shows all active Workstreams with status, current next action,
open NeedsOwner state, checkpoint recency, and open Run state.

The user may view any Workstream without changing durable state. Selecting a
row is navigation, not a business transition.

"Foreground Workstream" means the Workstream the user is currently operating
through the Web Surface. Phase 2.5 does not add a global CurrentFocus table.
The durable facts remain Workstream and Run state. If more than one Run is
already running, the Workbench displays that condition instead of silently
inventing a single authoritative focus.

The recommended day shape is one primary focus plus zero to two maintenance
items, but this is advice rather than a domain constraint. Margin must not hide
or block additional active Workstreams.

## 7. Resume Brief

### 7.1 Inputs

A Resume Brief is built from bounded, user-safe DTOs in this order:

1. current Workstream state, plan, blockers, and next action;
2. open or latest Run and latest Checkpoint;
3. unresolved NeedsOwner items;
4. active Decisions;
5. relevant Active Memory scoped to the Workstream;
6. recent user-safe Activity derived from Event Cursor.

The brief must not use the browser's previous conversation messages as
authoritative input.

### 7.2 Output

The brief answers:

- What is this Workstream trying to achieve?
- Where did work stop?
- Why did it stop or switch?
- Which decisions still apply?
- What is blocked or awaiting the owner?
- What is the recommended next action?

The recommendation contains one primary action and at most two alternatives.
Each recommendation includes bounded evidence references identifying whether
it came from Workstream state, Decision, Checkpoint, Event, or confirmed
Memory. It includes an evidence summary, not hidden reasoning.

### 7.3 Deterministic fallback

The Application layer assembles the verified brief facts before any model call.
Pi may compress and phrase those facts, but it cannot add unsupported facts.
When Pi is unavailable, the Workbench displays the deterministic structured
brief and remains usable.

### 7.4 User action

The user may accept, edit, or ignore the recommended next action. Accepting or
editing it uses a governed Workstream update with the latest expected version.
Ignoring a recommendation does not mutate durable state.

## 8. Safe Workstream switching

Switching is a host-owned application orchestration, not a browser-side series
of optimistic state changes.

When the user asks to operate another Workstream:

1. query the current Workstream and Run;
2. if the current Run is running, halt it through the existing Run control
   boundary and persist the resulting pause and Checkpoint;
3. do not activate the target while the current Run may still be executing;
4. query the target Workstream and build its Resume Brief;
5. resolve any open conflict or NeedsOwner item that prevents resumption;
6. on explicit user action, resume an eligible Run or create and start a new
   Run through the Gateway;
7. refresh authoritative state and Event Cursor before displaying success.

If pausing the source fails, the target is not started. If the source pauses
but target activation fails, the source remains honestly paused and the target
shows a retryable runtime failure. The UI must not claim an atomic switch that
did not occur.

Cross-Workstream memory, Decision, Artifact, NeedsOwner, Run, or Checkpoint
references are rejected. A brief for one Workstream must not contain another
Workstream's private context.

## 9. Minimal Memory Architecture

### 9.1 Boundary with other domain facts

Information belongs in:

- Workstream when it is current project state, plan, blocker, or next action;
- Run when it describes an execution attempt;
- Decision when it is an explicit choice that remains in force;
- NeedsOwner when a user decision or approval is pending;
- Event when it is a fact that a durable entity changed;
- Memory only when it is stable information likely to be useful in a future
  Session.

Raw conversation, daily progress logs, task lists, and generic summaries do
not become Memory merely because a model can summarize them.

### 9.2 Lifecycle

The user-facing lifecycle is:

```text
Candidate -> Active -> Archive
```

- Candidate is proposed and cannot be used as binding Personal Model evidence.
- Active has been explicitly confirmed and participates in default recall.
- Archive is retained but excluded from default recall. It is returned only by
  an explicit archive-inclusive search.

Correcting an Active Memory creates a new Active successor and marks the prior
record superseded. It never edits away the prior content or evidence. Archive
is reversible retention, not deletion; `memory.restore` can return a
non-superseded archived record to Active. Material deletion is outside this
phase.

The existing physical `proposed` and `confirmed` representation may be mapped
to Candidate and Active. Archive must have an explicit persistent state; it
must not be simulated by hiding a record in the Web client.

### 9.3 Scope

Phase 2.5 Memory remains Workstream-scoped. It does not automatically propagate
facts among job seeking, learning, and other projects.

Potential cross-Workstream Personal Model signals remain evidence attached to
their source Workstream. They cannot influence another Workstream until a later
phase adds an explicit user-confirmed global scope.

### 9.4 Provenance and recall

Every Memory DTO exposes bounded provenance, lifecycle state, version,
confidence, timestamps, and its source evidence coordinates. It never exposes
raw model internals.

Default recall searches Active Memory in the selected Workstream using the
existing project isolation, versioned hybrid retrieval configuration, Chinese
lexical fallback, expiry, and supersession rules.

Recall results include score, reason, and source. The UI must distinguish:

- recalled because of lexical overlap;
- recalled because of semantic similarity when embeddings are enabled;
- included because it is an explicitly confirmed active constraint or
  preference.

Archive is searched only after an explicit user request. Candidate Memory is
listed for review but is not returned as confirmed recall.

### 9.5 Application Contract extension

Memory becomes a first-class Application Contract capability for all Surfaces.
The Contract types frozen in Section 5 cover:

- list Candidate, Active, and Archive Memory by Workstream;
- search Active Memory and explicitly search Archive;
- confirm a Candidate with expected-version protection;
- correct or supersede an Active Memory without destroying history;
- archive an Active Memory with expected-version protection;
- restore a non-superseded archived Memory with expected-version protection.

Web code must not call `core.confirmMemory`, Memory tools, Store, repository, or
SQLite directly. Runtime tools may propose and search Memory only through their
existing governed adapter boundary.

### 9.6 Review experience

The Workbench adds a Memories view alongside Conversation, Artifacts, and
Activity. It provides:

- Candidate, Active, and Archive filters;
- confirmation, correction, and archive actions;
- explicit Active-only or Archive-inclusive search;
- provenance and recall-reason display;
- clear empty, stale-version, unavailable, and malformed-data states.

No candidate is automatically confirmed. A model must not forge the trusted
host confirmation context.

## 10. Conflict confirmation

Phase 2B reloads after `version_conflict`. Phase 2.5 turns that failure into an
explicit owner decision without allowing silent overwrite.

For an interactive Web conflict, the client retains only the temporary form
proposal, re-queries the authoritative DTO, and shows:

- the version the user originally viewed;
- the current Core value and version;
- the proposed change;
- actions to keep current, reapply explicitly against the latest version, or
  edit the proposal.

Reapply is an explicit new invocation of the original governed command, using
a new idempotency key and the latest expected version. It is not a separate
business command. The server never treats a stale command as implicit consent
to overwrite.

For a background or runtime conflict where the owner is not already present,
the Application layer may create a `NeedsOwner` item of type `conflict` through
the existing Gateway. Resolving the NeedsOwner records the choice but does not
fabricate a Decision unless an explicit Decision command succeeds.

## 11. Suggestion policy

A Phase 2.5 suggestion is bounded, evidence-backed, and optional.

- It contains one primary recommendation and at most two alternatives.
- It references current, user-safe domain evidence.
- It distinguishes confirmed evidence from an unconfirmed hypothesis.
- It does not claim that a suggested action occurred.
- It does not hide other active Workstreams.
- It cannot use Candidate Memory as a reason to hold or block an action.
- A high-risk or constitution conflict triggers explicit confirmation rather
  than covert refusal.

Phase 2.5 does not add an autonomous notification engine. "Proactive" means
that Margin presents a useful next-step recommendation when the user opens or
resumes a Workstream, without requiring the user to reconstruct the question.

## 12. Supporting daily views

Morning Portfolio may display all active Workstreams, unresolved NeedsOwner
items, and suggested priorities derived from current state. It may recommend
one primary focus and zero to two maintenance items, but the user remains free
to choose another combination.

Evening Review may derive a draft from that day's Events across Workstreams.
The user may correct it and set next actions. It does not create a separate
DayPlan database or treat generated prose as state.

These views are optional for Phase 2.5 acceptance. Switch and Resume is the
required loop.

## 13. Web composition

The Phase 2B three-column Workbench remains recognizable:

- left: active Workstream portfolio and status signals;
- center: selected Workstream, Resume Brief, and Conversation / Memories /
  Artifacts / Activity views;
- right: Run control, current plan, next action, NeedsOwner, and conflict
  confirmation.

The implementation should refine the existing composition instead of creating
a second dashboard or a separate memory application. Browser refresh may lose
temporary conversation display and unfinished forms, but must restore every
durable entity and the correct brief inputs from the Core.

## 14. Product-validation protocol

The owner uses several real Workstreams for up to 14 calendar days, seeking at
least 10 active-use days and at least 20 genuine Workstream switches.

After a resume, the owner records only:

- whether critical background had to be re-explained;
- whether the restored state was accurate;
- whether the suggested next action was accepted, lightly edited, or rejected.

The validation passes when:

- at least 80% of genuine resumes require no critical background
  re-explanation;
- at least 70% of primary next-action suggestions are accepted or lightly
  edited;
- the owner completes the switch-and-resume loop on at least 8 active-use days;
- at least one confirmed Memory is recalled correctly after a new runtime
  Session;
- at least one stale update exercises explicit conflict confirmation;
- no critical cross-Workstream leakage, fabricated state, silent overwrite,
  or unconfirmed-memory authority occurs;
- after the study, the owner chooses to keep using Margin without a study
  obligation.

These thresholds are internal product-validation criteria. They are not public
performance claims and do not retroactively validate earlier resume metrics.

Stop and reassess when:

- Margin is consistently slower than opening the underlying project directly;
- a Resume Brief is fluent but cannot support the next action;
- the loop requires a chat transcript or browser cache to remain accurate;
- memory confirmation becomes routine approval fatigue;
- three real-use days are abandoned because of Workbench interaction cost;
- success requires bypassing the Gateway or adding a second Source of Truth.

## 15. Testing and acceptance evidence

### 15.1 Contract and Core

Tests cover Memory DTO closure, capability ownership, Candidate / Active /
Archive transitions, expected versions, idempotency, correction provenance,
Archive-inclusive search, Workstream isolation, Event mapping, restart, and
safe failure envelopes.

### 15.2 Resume and switching

Tests cover deterministic brief composition, bounded evidence, runtime-offline
fallback, source pause before target activation, pause failure, target
activation failure, multiple-running-Run visibility, and no cross-Workstream
context.

### 15.3 Web

Tests cover portfolio selection without mutation, Resume Brief rendering,
accept/edit/ignore next action, Memories filters and review actions, archive
search, conflict comparison and explicit reapply, browser refresh, and all
empty/loading/error states.

### 15.4 Non-model E2E

An isolated temporary Core and fake runtime execute:

```text
create Workstreams A, B, and C
-> start work on A and persist state
-> propose and confirm an A-only Memory
-> switch to B, pausing and checkpointing A
-> verify B brief excludes A context
-> update B
-> restart browser and server
-> resume A with state, Decision, Checkpoint, and confirmed Memory
-> archive the Memory and prove default recall excludes it
-> explicitly search Archive and retrieve it
-> create a stale update and resolve it without silent overwrite
```

### 15.5 Live Pi validation

One isolated credential-gated run verifies that a new Pi Session can receive a
bounded Resume Brief, recall one confirmed Workstream Memory through governed
tools, and persist only successful tool changes. The evidence remains
sanitized and must not contain credentials, prompts, assistant prose, Pi
objects, or hidden reasoning.

### 15.6 Regression

The Web build, full automated suite, Stage 1 validation, Pi baseline audit,
restart tests, and diff checks must pass. Test counts are reported from the
actual acceptance run rather than copied into documentation.

## 16. First public GitHub release claim boundary

The accepted repository must visibly demonstrate the functional claims in the
owner's resume:

- Pi Agent integration using governed Session and tool boundaries;
- structured project state;
- cross-Session and cross-switch continuity;
- on-demand confirmed-memory recall;
- evidence-backed next-action suggestions;
- write gates and host confirmation;
- version history and optimistic conflict handling.

README and demo material must distinguish implemented functionality,
automated-test evidence, isolated live smoke evidence, and external user-study
claims. Phase 2.5 does not fabricate or attempt to recreate the resume's
historical numerical results. Public metrics are included only when their
method and evidence are available.

The release includes one reproducible local demo path for the A -> B -> A
switch-and-resume scenario and lists its safety boundaries and non-goals.

## 17. Non-goals

Phase 2.5 does not implement:

- a global Personal Model or automatic cross-Workstream memory;
- Personal Constitution administration UI;
- Feishu or another mobile Surface;
- Scheduler, overnight execution, or push notifications;
- multi-Agent orchestration;
- Shared Workspace writes or arbitrary filesystem access;
- a universal inbox;
- persistent Conversation transcripts;
- a separate Activity, suggestion, daily-plan, or vector database;
- public claims based only on model output or test fixtures.

## 18. Recommended technical route after Phase 2.5

The previous roadmap's immediate Shared Workspace phase is deferred. The
recommended sequence is:

1. Phase 2.5: Multi-Workstream Continuity Validation and first public release.
2. Phase 3A: user-confirmed Personal Model scope, personal constitution, and
   Decision outcome learning, only after continuity evidence passes.
3. Phase 3B: Feishu capture and notification Surface if the pilot identifies
   mobile input friction as a leading cause of missed use.
4. Phase 3C: Scheduler-prepared Morning Portfolio and Evening Review drafts
   after the manual versions prove useful.
5. Phase 4: Human-Agent Shared Workspace and broader execution capability after
   checkpoint, stop, conflict, and owner-control behavior remain reliable in
   real use.

Phase 3B may precede Phase 3A only if the Phase 2.5 evidence shows that access
friction, rather than continuity quality, is the main adoption constraint.

## 19. Phase 2.5 acceptance

Phase 2.5 is complete when:

1. several Workstreams can be inspected and switched without context leakage;
2. the source Run is safely paused and checkpointed before target activation;
3. Resume Brief works with deterministic facts when Pi is unavailable;
4. evidence-backed recommendations can be accepted, edited, or ignored;
5. Candidate, Active, and Archive Memory are visible and governed through the
   Application Contract;
6. confirmed Memory is recalled across a new runtime Session and Archive is
   excluded by default;
7. stale writes require explicit conflict handling and never silently
   overwrite current state;
8. browser and server restart restore all durable state;
9. the complete automated and isolated live acceptance evidence passes;
10. README and demo claims match implemented, reproducible behavior;
11. the product-validation protocol can begin without a second state system;
12. implementation stops before Personal Model, Feishu, Scheduler, or Shared
    Workspace expansion.
