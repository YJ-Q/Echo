# Margin 项目理解手册设计规格

日期：2026-07-30  
状态：已完成对话设计确认，等待书面规格确认

## 1. 背景

Margin 已经具备中文、英文 Case Study、证据映射、可运行产品、自动化测试和多份产品设计文档。现有 Case Study 擅长解释产品为何存在、定位如何收紧、产品原则如何约束功能，以及当前证据能支持哪些结论。

现有材料仍不适合作为项目创作者的系统教材。它没有逐项解释主要技术选型的候选方案、现实约束、代价、风险和重评条件，也没有提供一条从用户操作进入真实代码的完整阅读路线。

本项目将新增一套中文“Margin 项目理解手册”。它服务于项目创作者本人，帮助其从零建立产品、策略和技术三层认识，并最终能够脱离文档独立解释项目。

## 2. 目标与成功标准

### 2.1 核心目标

手册需要帮助读者回答：

1. Margin 为什么这样定义产品，而不是成为通用聊天、任务管理或治疗替代工具？
2. 到场、活线、选择性记忆、低压力继续和痕迹式反思为什么这样设计？
3. 当前架构与主要技术选型为什么适合项目现阶段？
4. 每项选择的代价是什么，什么条件出现时需要重新评估？
5. 一次真实用户交互如何经过前端、API、服务、数据库、模型和状态聚合？

### 2.2 成功标准

- 使用中文，从零解释，不假设读者掌握后端、数据库或 AI 架构。
- 每项重要技术结论至少链接一个真实源码、配置、测试或 Git 证据。
- 明确区分事实、合理推断和待创作者确认的历史动机。
- 读者能够按代码阅读路线追踪一条完整主链路和主要失败路径。
- 读者能够通过自测题和能力清单验证自己是否真正理解项目。
- 不把自动化与场景验证误写成真实用户价值或市场验证。

## 3. 非目标

- 不重写现有招聘版 Case Study。
- 不把手册写成框架或编程语言的通用教程。
- 不为仓库中无法证明的历史决策编造动机。
- 不在本阶段修改产品功能、架构或运行行为。
- 不把尚未合并的独立分支能力描述成当前主线已经拥有的能力。
- 不替代 API 合同、部署指南、备份指南等操作文档。

## 4. 核心读者与写作深度

核心读者是项目创作者本人。手册采用“从零解释，最终落到真实代码”的深度：

1. 先用非技术语言说明问题。
2. 使用简单比喻建立直觉，但不让比喻替代准确机制。
3. 比较候选方案和现实取舍。
4. 展示当前选择及其代价。
5. 链接对应代码、测试与配置。
6. 给出重评条件和理解检查。

面试表达不是主导目标。手册完成后可从其中抽取面试答案，但正文优先保证理解准确、证据完整。

## 5. 内容架构

### 5.1 三层认识

- **产品层：**用户处境、定位、品类边界、MVP 范围和待验证假设。
- **策略层：**产品原则如何转化为 AI 行为、信息层级、记忆规则、行动规则和失败回退。
- **技术层：**系统架构、数据流、技术选型、兼容机制、测试方法和演进条件。

### 5.2 主手册八章

1. **项目全景**  
   解释 Margin 的定位、当前阶段、主要能力和 Implemented / Scenario-validated / Hypothesis 三层证据边界。

2. **问题与策略**  
   解释为什么项目不是通用聊天、任务管理器或治疗替代品，以及“第二自我”的责任边界。

3. **核心产品闭环**  
   解释到场、保留活线、选择性记忆、轻量继续、留下痕迹的因果关系。

4. **系统地图**  
   解释浏览器前端、Express API、服务层、SQLite、LLM Provider 和 Electron 的职责与边界。

5. **一次请求的旅程**  
   追踪用户输入如何经过路由、聊天服务、输入分析、上下文构建、模型生成、状态写入、状态聚合和前端呈现。

6. **技术决策**  
   通过标准决策卡解释关键技术选择、替代方案、代价和重评条件。

7. **质量、兼容与风险**  
   解释测试分层、数据隔离、备份恢复、配置兼容、错误处理、动态端口和隐私边界。

8. **演进路线**  
   区分当前限制、文档债务、未整合分支、待验证产品假设和可能触发架构升级的条件。

## 7. 标准决策卡格式

每张决策卡使用相同结构：

1. **决策问题：**需要解决什么问题。
2. **当时约束：**项目阶段、人员、成本、部署、隐私和维护限制。
3. **候选方案：**至少比较当前方案与一个可信替代方案。
4. **当前选择：**仓库实际使用的方案。
5. **选择理由：**只写证据支持的事实或明确标注的推断。
6. **收益：**当前方案解决了什么。
7. **代价：**复杂度、性能、扩展性或维护成本。
8. **失败风险：**方案在什么场景下会失效。
9. **代码证据：**对应源码、配置、测试和文档。
10. **重评条件：**用户量、数据规模、协作方式或产品方向达到什么条件时重新选择。
11. **理解检查：**要求读者用自己的语言解释，而不是复述术语。

## 8. 主链路与失败路径

### 8.1 主链路

```text
用户输入
→ 前端请求
→ Express 路由
→ chatService
→ 输入与意图分析
→ 上下文与记忆召回
→ Provider 选择与回复生成
→ 记忆、学习、行动等状态更新
→ /state 聚合
→ 前端呈现当前活线
```

手册需要在每一步说明：

- 这一层负责什么；
- 为什么不由相邻层负责；
- 输入和输出是什么；
- 对应的真实文件在哪里；
- 哪些测试证明其限定行为。

### 8.2 必讲失败路径

- 未设置远程模型 API Key。
- 外部模型请求失败。
- 新数据库不存在但旧数据库存在。
- 旧数据库为什么只回退而不自动迁移。
- 备份、导入和兼容 API 如何限制风险。
- Case Study 和测试如何避免读取真实用户数据。
- 动态端口、ready 所有权和超时清理如何避免误判。
- 缺少信息时，系统如何避免制造记忆、洞察或行动。

## 9. 证据与诚实性规则

每项重要论述标记为以下一种：

- **事实：**可由当前主线代码、测试、配置、操作文档或 Git 历史直接证明。
- **合理推断：**从实现与约束推导出的设计理由，必须显式标注“推断”。
- **待确认：**仓库无法证明的历史动机，转化为创作者复盘问题。

证据优先级：

1. 当前主线的运行代码和测试。
2. 当前配置与 API 合同。
3. 已完成规格、验收记录和 Git 历史。
4. Case Study 中已映射的产品结论。
5. 未整合分支只能用于说明候选演进，不能描述为当前能力。

若文档和代码不一致，以当前代码与测试为准，同时记录文档债务。

## 10. 学习体验

每章采用固定循环：

1. 现实问题；
2. 直觉解释；
3. 系统图或调用链；
4. 候选方案；
5. 当前选择和代价；
6. 代码与测试证据；
7. 条件变化思考题；
8. 自己复述。

手册避免连续堆叠术语。术语首次出现时使用中文解释，必要时保留英文原词，之后保持一致。

图示只用于帮助理解三类关系：

- 系统层级和职责；
- 一次请求的顺序；
- 决策条件变化后的分支。

不为装饰而增加图示。

## 11. 质量验证

完成后执行以下检查：

- 所有本地文件链接存在。
- 所有代码路径属于当前主线或明确标记为候选分支。
- 每张决策卡包含代价、失败风险和重评条件。
- 不存在未说明的 TBD、TODO 或占位文本。
- 不把测试通过、场景验收或部署成功解释为用户价值成立。
- Case Study 的招聘叙事与理解手册的教学叙事不互相覆盖。
- 自测题能够覆盖产品、策略、技术和演进四种理解。
- 文档修改不影响产品测试；仍运行完整 `npm test` 作为仓库级回归检查。

## 12. 范围控制与实施顺序

实施按以下顺序进行：

1. 建立当前主线架构和证据清单。
2. 编写主手册的产品层、策略层和系统地图。
3. 追踪并验证一次请求主链路。
4. 编写十二张技术决策卡。
5. 编写失败路径与风险章节。
6. 编写代码阅读路线。
7. 编写自测题与能力清单。
8. 检查链接、事实分类和文档一致性。
9. 运行完整测试并进行独立内容审查。

首版不扩展为视频课程、交互式教程、英文版或新的 Case Study 网站栏目。只有当中文静态手册能够完成学习目标后，再评估其他形式。
