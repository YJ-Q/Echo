# Margin 原始 MVP 收口与底座选型设计

## 目标

先完成并验证现有单项目终端连续性 MVP，再使用相同 Margin Core、数据、工具和测试输入比较 Pi Agent、DeepSeek Harness 与 Codex 开源项目。底座确定前不实现正式前端、多项目自动路由或完整产品架构。

## 本轮完成边界

### 原始 MVP 收口

- 维持一个 `career_project` 终端试点，不新增业务专用数据结构。
- 保留四个模型可见工具：`memory_search`、`memory_propose`、`state_update`、`action_update`。
- 验证状态更新、行动更新、候选记忆确认、中文召回以及新 Session 恢复。
- 验证普通聊天不自动进入长期状态，无相关记忆时返回空结果。
- 保留项目隔离、来源、版本、审计、高风险确认和内置高风险工具禁用边界。
- 修正文档中已经与实际实现不一致的“尚未实现”状态，但不扩大能力声明。

### 关键验收

采用少量真实试点和自动化回归完成技术验收：

1. 在 Session A 记录真实任务进度和下一步行动；
2. 提出并由宿主确认一条长期记忆；
3. 在 Session B 恢复同一任务、开放行动和相关已确认记忆；
4. 输入普通聊天，确认没有持久化污染；
5. 保存脱敏 Trace、配置、实体版本和审计编号。

本轮不要求 50—200 个冻结任务、成功率指标或 5 人 × 7 天研究。它们属于底座确定后的正式评测，不能由当前技术烟雾测试替代。

## 底座评估设计

### 共同控制面

三个候选底座必须复用同一套：

- Margin Core 与 SQLite 测试数据；
- 四工具定义、宿主权限和确认机制；
- 模型提供方、模型版本、参数和输入；
- 单项目跨 Session 场景与期望结果；
- 脱敏日志格式和判定规则。

底座只能负责 Agent 循环、模型调用、Session/压缩生命周期与工具协议适配。Margin 继续负责结构化状态、记忆、权限、确认和审计。

### 比较维度

- 集成和维护成本；
- Session、分支及上下文压缩支持；
- 工具协议稳定性与宿主权限控制；
- Trace、错误分类和可观测性；
- Provider 兼容性与模型替换成本；
- 终端、未来桌面端和移动入口适配；
- 上游活跃度、许可证、版本锁定和迁移风险；
- Margin Core 与底座解耦程度。

不使用不同模型的回答质量证明某个底座更优。无法在相同条件下实测的项目必须标为“未验证”，不能按成功计分。

### 执行顺序

1. 以现有 Pi 适配器形成基准；
2. 核实 DeepSeek Harness 与 Codex 开源项目的具体仓库、版本和许可证；
3. 为每个可行候选实现最薄适配或最小 spike；
4. 运行相同关键场景并记录差异；
5. 输出决策矩阵和 ADR，选定一个主底座并保留明确回滚边界。

## 延后事项

- 多项目管理以及自动项目/任务归属路由；
- 完整产品方案中的主动建议、复杂领域工具和正式前端；
- 招聘网站、邮箱、文件或其他外部账号写入；
- 50—200 个冻结任务与真实用户连续研究；
- 简历中的效果数字和未经验证的产品价值结论。

底座确定后，再结合用户提供的完整产品与技术架构方案设计这些能力，避免被当前 Pi 适配结构锁定。

## 退出条件

- 原始单项目连续性关键闭环可重复运行；
- 文档中的已实现、未实现和贡献边界与代码一致；
- 三个候选底座均有可追溯的版本、许可和可行性结论；
- 至少对可运行候选完成同条件最小验证；
- 形成有证据支持的底座 ADR；
- 在 ADR 完成前不启动自动项目路由或正式前端开发。
