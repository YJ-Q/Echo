# Margin 产品与架构设计原则

本文件记录跨切片、长期有效的设计原则，不记录单个 Slice 的实现细节或分析过程（那些放在 `docs/architecture/`）。

---

## Research-first, reuse-first, compare-after

日期：2026-09-06

对于 Margin 的重要产品与架构设计（尤其是涉及外部 Coding Agent 数据格式、语义解析、成熟生态已有解决方案的场景）：

1. 先研究官方实现、成熟开源项目和同类产品；
2. 理解其数据来源、边界和设计原因；
3. 能复用则优先复用；
4. 只针对 Margin 的真实差异做最小优化或创新；
5. 完成后与原方案对比实际效果；
6. 除非已有方案无法满足需求，否则不从零重新设计。

### 为什么

Slice 2.1 曾经用一条固定正则识别 Codex 的某个内部审批消息文案。这只解决了已观察到的一个具体案例，一旦文案变化或出现新的内部消息类型就会失效——本质是在给一个上游已有稳定语义字段（Codex 自己的 `thread_source`）的问题打局部补丁。Slice 2.2 改为先研究 Codex 原生记录结构和 `continues` 已有的处理方式，确认二者都不提供所需字段后，才在 Margin 自己的 source boundary 上做最小新增。

### 如何应用

- 遇到"某个 Agent/工具的数据里有一种奇怪情况"时，先确认：官方是否已经有稳定字段/结构表达这个语义？`continues`（或其他已引入的成熟依赖）是否已经处理、部分处理、或明确没有处理？
- 只有在确认现有方案覆盖不到时，才在 Margin 自己的代码里新增判断逻辑，且优先放在最接近数据源头的边界（source boundary），而不是放在最终展示/裁剪层。
- 文本关键词匹配（regex 识别具体文案）是没有更可靠信号时的最后手段，不是默认方案；引入时要明确写清楚它在覆盖什么"已知结构信号覆盖不到"的缺口，而不是覆盖所有情况。
